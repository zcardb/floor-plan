# 系统提示词升级：住宅户型与家具布局规划规则

## Context

当前 AI 设计的两份系统提示词（`PLAN_CONTRACT` 整户户型、`ROOM_CONTRACT` 单房间）里，规则密集但偏「设计经验」：生活常识、门窗优先级、分区建议混在一起，缺少统一的约束分级、碰撞与净空检查口径、修正顺序与自检状态，导致模型偶尔会用「收纳更多、布局更对称、房间更宽敞」换取堵门、穿墙、挡窗这类硬伤。

用户提供了一份完整的《住宅户型与家具布局规划助手》提示词，要求把它作为系统提示词，并结合本项目已有约定落地。本次改动只动提示词与后端校验口径，不改数据格式、前端 schema 与交互。

已确认的决策：

- 作用范围：整户户型（plan）与单房间（room）都替换，公共规则抽成一个共用块。
- 检查结论（通过／冲突／信息不足／不适用）只作为模型内部自检，不进入 JSON 输出。
- 允许「椅子部分收进桌下」等正常重叠：按家具类型调整后端校验器。
- 门铰链侧：允许模型在用户给出开向信息时输出 `hinge`（schema 已支持）；不新增其他缺失数据字段。

## 必须保留的现有约定（不得改动）

- 单位 mm；原点在室内净轮廓外接矩形左上角；x 向右、y 向下（下方为南）。
- 家具只能用目录代号 `F*`，尺寸固定取目录值（`code/back/along/gap`；`back` = up/down/left/right）。
- 整户输出：`summary / width / depth / outline? / walls / rooms / openings / furniture`；外墙 top/right/bottom/left 或 `ek`；内墙 `dir=h|v`、`at/from/to`，取墙中心线；`mat` 取固定材质枚举。
- 房间轮廓沿墙中心线、贴外墙的边落在外轮廓坐标上；门窗 `at/width`、门 `into`（横墙 up/down，竖墙 left/right）；窗只在外墙上。
- 用户指定的门窗位置、宽度、开向是最高优先级硬约束，不得挪动、增删、改尺寸（含 `DOOR_RULE` 结尾重申）。
- 「指定家具」不为空时，种类与件数必须与清单完全一致（硬校验，`validateRoom`）。
- 生成流程：多轮修复（`repairRounds`）、hard/soft 两级校验、取「hard 最少、其次 soft 最少」的一版、只输出 JSON。
- 信息不全时不提问，按常见住宅做法合理假设。
- `SIZE_LINE`（用户给了长宽／面积就按用户的）、`DIRECTIONS`（同批候选差异化思路，仅体现在分区与家具上）保留。

## 改动文件

`supabase/functions/interior-ai-design/index.ts`（唯一需要改的文件；提示词只存在于这里）

## 实施设计

### 1. 新增共用块 `PLANNING_RULES`

把用户给的新提示词整体改写为一个共用常量，放在 `LIVING_SENSE` 旁边，覆盖以下小节（保持用户原文的严谨口径与检查项，逐条对齐本项目数据能力）：

1. 角色与目标：住宅户型与家具布局规划助手；只处理空间结构、尺寸、位置、朝向、功能关系、可行性；不讨论风格、配色、材质、渲染。
2. 约束分级：必须保留／允许调整／尚未确认；硬约束不得被「收纳更多、布局更对称、房间更宽敞」等优点抵消；区分物理约束、使用约束、布局偏好；不把「所有家具靠墙」「床必须居中」「窗前一律不放东西」当普遍硬约束。
3. 空间模型：统一 mm；坐标基准不得混用；家具正面方向与旋转后占地同步；区分建筑外轮廓、墙中心线、室内净尺寸（本项目：墙与房间按中心线，外墙在外轮廓之外，家具落在房间净空内）；家具归属按完整占地轮廓判断；开放式客餐厅按实际可用边界处理，不把功能分区线当实体墙。
4. 建筑边界与房间：不越界、不重叠；墙柱管井不属净空间；相邻房间共用墙位置一致、无错位与夹缝；每个独立房间有可达入口；门窗只能落在实际存在的墙段上、不与柱管井冲突；不得为放家具挪动固定墙体门窗。
5. 家具碰撞：不穿墙穿柱、不越出边界、不跨越实体隔墙、不侵入其他独立房间；不嵌入墙体；家具之间不实体穿插；旋转后按旋转后占地检查；不得缩小或修改已知尺寸；桌面物品须有承托面、壁挂须有安装面。
6. 允许的正常重叠：地毯可位于床／沙发／桌椅下方；椅子可部分收进桌下（后端校验同步放行，见第 3 点）；桌面物品可位于桌面范围内；柜门／抽屉与其上方吊柜按支撑关系与垂直净空判断；不得仅凭二维投影重叠判定碰撞，也不得仅因高度不同忽略支撑、操作与通行。
7. 门与出入口：门洞、门扇扫掠区（按铰链侧与开向）、推拉门滑动路径与其他门型的实际展开方式；人能否接近门、操作门并通过；两门相互干扰需指出；不得占用门洞通行开口，门洞前通行沿用现有 ≥800 mm；不得靠改变门的开启方向消除冲突；门型或开启方向未知时不得声称已完成门扇碰撞检查。
8. 窗与窗前区域：高柜（衣柜、书柜、冰箱等）不得遮挡窗洞，不得用柜体背板／侧板覆盖窗洞；矮柜、书桌可作窗下候选，但须同时满足不挡窗扇开启、可接近把手、不妨碍通风清洁；内开窗检查室内扫掠、外开窗与推拉窗检查把手操作与维护路径；不得封住唯一必要的开窗操作路径；落地窗与可通行玻璃门区分，后者按出入口处理；家具高度、窗台高度、窗型未知时按家具类别保守判断（高柜默认避开窗前），不得宣称窗前布置已通过、不得编造高度数值。
9. 柜体、抽屉与设备：正面朝可接近空间、不被其他家具封住；平开柜门检查开启范围与柜前站位、推拉柜门保留站位取物空间、抽屉检查完全拉出；转角处受相邻墙面／柜体限制；冰箱洗衣机洗碗机洗碗等按实际门型检查取物；不遮挡开关、控制面板、阀门、通风口与检修口；散热与维护净空以已给产品要求为准，不编造统一数值。
10. 家具实际使用空间：桌椅可拉出、坐下、起身，且有人就座时周边仍满足必要通行；书桌下保留腿部空间；床有正常上下床路径（双人床两侧、单人床至少一侧 ≥500 mm，沿用现有数值）；床与衣柜距离同时考虑床占地、柜门／抽屉开启与操作；沙发座椅的可接近方向；餐桌按实际可拉椅位置计算有效座位；折叠床、沙发床、伸缩桌需分别检查收起、展开与转换过程；不得用收起尺寸证明展开可用；功能关系匹配（椅子对应桌面、柜子从使用面取物）；只在不同时间使用的操作区可部分重叠但要说明条件；必须同时进行的活动不得相互阻断；不得靠每天搬动大型家具满足基本功能。
11. 通道与可达性：从入户门到各独立房间、从房间门到主要家具使用面存在连续路径；按人的通过宽度判断，不以无宽度线段连通为合格；检查最窄处、转角与家具突出部件；不得要求跨越床／沙发／柜体、钻过桌子、穿过家具实体；家具增减后重查通道；沿用现有数值（主通道净宽 ≥700 mm）。
12. 尺寸与净空：优先用户实测、已确认规格与目录尺寸；每个净空参数标注适用对象与方向（柜前操作、床侧通道、椅后空间等），不用单一数值替代全部要求；区分家具实体范围、开启范围、使用范围、通行范围，分别检查后判断可否按时序共享；检尺寸时必须连同相邻物体一起看；已知尺寸不得为凑布局修改；缺关键尺寸时按常见住宅做法保守假设并说明依赖假设（本流程不提问）。
13. 生成与校验流程：先确认固定边界、障碍物、门窗与必须保留的物品 → 整理家具尺寸、使用面、开启方式与净空 → 先预留出入口、门扇开启区、必须保护的窗前区域与主通道 → 先放尺寸大／位置受限／依赖固定设施的物品 → 再布置其他家具 → 每次移动、旋转、替换、新增后重查受影响约束 → 输出前完整自检（不得只验最后修改的物品）。
14. 冲突修正顺序：移动家具 → 调整朝向 → 调整同一功能区的组合 → 改用满足功能的规格 → 减少非必要物品 → 改动用户允许调整的条件；不得删除必须保留的家具、缩小已知尺寸、移动固定门窗、忽略硬约束；每修正一处后检查是否产生新的碰撞、遮挡、操作冲突或通道问题；无法同时满足时指出冲突对象、位置与需调整的条件，优先保证门窗与用户硬性要求，给出最接近的可行方案，不输出明知不成立的方案。
15. 输出纪律：以上检查项用 通过／冲突／信息不足／不适用 判断，只作为内部自检，**不写入 JSON**；没有发现问题不等于已通过（缺高度、门窗开向等信息时不得默认通过）；输出必须严格遵守对应模式契约的 JSON 结构，不新增字段，不做解释性文字。

### 2. 重组 system 组装与两份契约

- `system` 顺序改为：`PLANNING_RULES` → `LIVING_SENSE` → 模式契约（plan/room）→ `agent.instructions` → 小助手要求 →（用户消息末尾仍是 `DOOR_RULE`）。
- `LIVING_SENSE` 保留功能房间的配置常识（床／沙发／灶台／马桶朝向、动线、采光），去掉与共用块重复的门窗与高柜挡窗表述，避免同一规则两处出现。
- `PLAN_CONTRACT` 精简为：角色 + 需求理解（外轮廓形状、门窗还原优先级、硬要求与偏好的区分、参考图与附件户型图处理）+ 分区（功能关系、动线、采光、面积比例、走廊、剩余空间用途）+ 几何约定 + 输出约定（原有 JSON schema 全文保留）+ 模式自检清单；删除与共用块重复的碰撞、门窗、生活常识条目。
- `ROOM_CONTRACT` 精简为：角色 + `zone / back / along / gap` 的换算与取值边界（含「贴墙 gap = 0、家具宽沿背靠边、尺寸取目录值」）+ 与整套户型的一致性 + 指定家具件数规则 + 输出格式 + 自检提示，其余全部引用共用块。
- 在输出约定里补一句 `hinge` 用法：门的 `into` 与 `hinge` 只在用户明确给出开向／铰链侧时输出，`hinge: "start"` 表示洞口靠墙 from→to 中坐标较小的一端（横墙为 x 较小端、竖墙为 y 较小端），`"end"` 为坐标较大端；未给出时省略（系统默认 start）。
- 保留 `SIZE_LINE`、`DIRECTIONS`、`DOOR_RULE`、`MAX_TOKENS`、修复轮逻辑不变。

### 3. 校验器按类型放行正常重叠（`checkItems`）

现状：`if (e.type === 'rug' || other.type === 'rug') continue;`，其余重叠 >50×50 mm 记为 soft。

改为：地毯照旧跳过；再新增「椅子部分收进桌下」放行——当一对家具一件属于椅类 `chair / officechair / barstool`、另一件属于桌类 `table / roundtable / coffeetable / desk / island / counter`，且椅子的占地没有被桌子完全包含、在至少一个方向伸出 ≥100 mm 时，不记 soft。其余重叠判定与阈值不变（不新增 hard 规则、不放宽越界检查）。

### 不改动

前端 `src/features/interior/ai/*`（`sanitize.ts`、`apply.ts`、`context.ts`、`types.ts`）与 `interior_ai_*` 表结构；`hinge` 前端解析已支持，无需改。
